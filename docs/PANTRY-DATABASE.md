# Persistent pantry directory

Reach extends the existing SQLite database instead of maintaining a second pantry store. `openPantryDatabase()` calls `openCommunityDatabase()` using `REACH_COMMUNITY_DB` (default `.local/community.sqlite`), initializes the additive account schema, then applies numbered pantry migrations inside `BEGIN IMMEDIATE` transactions. Foreign keys, WAL, a busy timeout, full synchronization and private file permissions are inherited from the existing connection. Use Node 24 (the project engine and `.nvmrc`) with the built-in `node:sqlite` module and a persistent, private writable volume. SQLite suits the existing single deployment; multiple independent writers across hosts require a shared database migration before horizontal scaling.

The runtime migration definition is `pantryMigration1` in `src/lib/pantry-store.ts`; `migrations/pantry-001.sql` is its equivalent SQL artifact. Do not execute that SQL against an already migrated database. `pantry_migrations` records applied versions. Future schema changes must append a numbered migration rather than editing version 1.

## Import and preservation

Run `npx tsx scripts/import-pantries.ts [database-path]`. Opening the pantry database automatically imports the 24 maintained source records (the original eight plus the regional expansion). Each import inserts a pantry with `INSERT OR IGNORE`; only a newly inserted record receives its original schedule and first history snapshot. Repeating the import never replaces edits, hours, closures, archive status, or inventory. It preserves existing IDs, source URLs and checked dates; `lastVerified` and initial update time derive from the existing latest checked date. The initial timestamp describes the source review, not a provider contact. No inventory or visitor observations are generated.

The source `Resource` is retained as JSON, original planner metadata as separate JSON, and operating windows, closures, inventory, manager assignments, favorites, corrections, audit entries and version snapshots in relational tables. Planner reads use the current active directory and current windows/closures while retaining document, appointment, pedestrian access and source metadata. Existing schedule conflicts remain present. Empty hours and inventory remain unknown. Current planner sources retain original identifiers only while their matching URL/title remains in the current listing; deleted source evidence cannot silently reappear from the original snapshot. Reviewed walking connections are used only while both the current address and coordinates exactly match the source snapshot. A move quarantines both direct walking and transit access paths until a new route review; the original snapshot remains available for audit. Changing structured hours regenerates both the public hours and schedule notes, replacing old seed exceptions while preserving source conflicts explicitly supplied in each window. Editing notes updates public schedule uncertainty. A changed freeform hours field clears old normalized windows conservatively while retaining recorded closures; structured hours must be saved before the planner can use a schedule again.

`listPantryResources(db?)` and `listPlannerPantries(db?)` exclude archived records. `getPantryRecord(id, db?)` is an internal lookup that may return an archived record; callers must apply visibility rules. Public APIs enforce those rules. `canEditPantry(db, actor, id)` requires a verified email and either the administrator account role or a pantry assignment. Community moderator privileges are independent and grant no pantry access.

## HTTP contract

All endpoints are under `/api/pantries`. Responses disable caching. Every mutation requires a JSON body of at most 64 KiB and an Origin matching the canonical `REACH_APP_ORIGIN` (or existing `REACH_COMMUNITY_ORIGIN` fallback); browser cross-site mutations are refused. The shared account-origin helper ignores forwarded headers. Unconfigured local development accepts only a validated direct loopback Host/request URL; invalid configuration and unconfigured production fail closed with HTTP 503. Payloads are strict Zod schemas and SQL parameters never include user-controlled identifiers. Signed-in mutation limits persist in SQLite. The frontend contract is `src/lib/pantry-types.ts`. Every detail/directory pantry includes computed `scheduleSources: SourceRef[]` so an hours editor can select the current source by title while saving its exact identifier. Original source identifiers remain stable; newly added sources use a SHA-256 identity of their URL (or title when no URL exists), so reordering is safe and replacing evidence invalidates old references. These references are computed from current sources and the immutable source snapshot, not stored as another source list. They do not establish verification beyond the supplied attribution.

- `GET /`: `{pantries, page, total}`, with `query` (or `q`), `page` and `pageSize` (1–100, default 50). Public results contain active records only. `includeArchived=true` requires administrator or assigned-manager access and returns only permitted records.
- `GET /:id`: `{pantry, inventory, permissions: {canEdit, isAdmin}}`. Archived records require editing permission.
- `POST /`: verified administrator only. Accepts pantry description/contact/source fields; requires name and address. Coordinates default to null, hours/eligibility to explicit unknown values, and sources to an empty array. No unverified hours are invented.
- `PATCH /:id`: assigned verified manager or administrator. Accepts fields in `PantryPatch`; requires the current `version`. Unknown fields, role fields and archive flags are rejected.
- `PUT /:id/hours`: `{windows: PantryWindow[], closures: YYYY-MM-DD[], version}`. Uses the recurrence rules already understood by the planner. Empty windows mean unknown hours. These are wall-clock service times in America/Chicago.
- `PUT /:id/inventory`: `{items: [{category,status,quantity,source,updatedAt?}],version}`. Status is available, limited, unavailable or unknown. Quantity is null or a nonnegative integer. Each save replaces the current category list. The server stamps update time; client timestamps do not establish freshness.
- `POST /:id/archive` and `/restore`: administrator only, `{confirmation: pantry.name}`. Soft deletion preserves all history. Exact pantry name confirmation is mandatory.
- `POST /:id/corrections`: verified signed-in account, `{description}`. Creates a pending proposal without changing official information.
- `GET /corrections`: administrator only, `{corrections,page,total}`, with pending suggestions first.
- `POST /corrections/:correctionId/review`: administrator only, `{decision: "approve"|"reject", notes, changes?: PantryPatch}`. Approval requires an explicit validated patch and matching version; rejection cannot carry changes. Review and edits commit together, and already reviewed proposals cannot be reviewed again.
- `GET /management`: verified administrators or assigned managers, `{pantries,page,total}` including permitted archived records. Supports directory search/pagination.
- `GET /assignments`: administrator only, `{assignments:[{pantryId,userId,email,name}],page,total}`.
- `POST /assignments`: administrator only, `{pantryId,email,assign}`. The email must belong to an existing verified account. Assignment grants access to that pantry without changing account roles.
- `GET /audit`: administrator only, `{audit:[{id,actorId,action,pantryId,details,createdAt}],page,total}`.
- `GET /favorites`: signed-in account, `{favorites: string[], pantries: PantryRecord[]}`. Active favorites only.
- `POST /favorites` and `DELETE /favorites`: signed-in account (verification not required), `{id}`. Changes apply only to the session account. Foreign keys remove favorites and assignments on account deletion; historical editor references become null.

All official changes append a full pantry/inventory version snapshot and an audit entry in the same transaction. Stale versions receive HTTP 409 and must be refreshed. Corrections and assignments are audited separately. Audit content is restricted to administrators; do not expose those endpoints in public cache layers.

## Backup and rollback

Before a deployment migration, stop application writers and back up the database with SQLite's backup API (`DatabaseSync.backup` where supported), the SQLite CLI `.backup`, or a coherent volume snapshot. Do not copy only the main `.sqlite` file while WAL writes are active. Store backups privately; the shared database contains account/session data. Test restore on an isolated copy with foreign-key checks (`PRAGMA foreign_key_check`) and the pantry integration tests.

Migrations are forward-only. To roll back a failed deployment, stop writers, restore the complete pre-migration database backup, and restore the matching previous application version. Restoring only pantry rows can lose review/history relationships and is unsupported. Prefer restoring an archived pantry through the audited restore endpoint for ordinary listing mistakes. Do not rerun the original import as an undo operation: it intentionally preserves edits and archives.

## Validation

`npx vitest run tests/pantry-database.test.ts` exercises the actual SQLite handlers and import, source preservation, manager ownership, moderator separation, optimistic locking, archive/restore history, reviewed corrections, hours/inventory, favorites privacy/cascade, strict inputs, same-origin checks and request size limits. No external service credentials are needed for these checks.

## Private food-access inquiries

The optional outreach module initializes its own additive `outreach_recipients`, `outreach_threads`, `outreach_replies`, `outreach_events` and `outreach_limits` tables in the same database. Idempotent column checks add authorization expiry, approved-contact fingerprints and consented pickup coordinates. This does not change pantry migration version 1, overwrite maintained pantry data or populate production recipients/inventory. The deterministic planner itself stores no starting locations.

See [the food-access planner guide](ACCESS-PLANNER.md) for workers, enrollment, receiving setup, cancellation, suppression, single-host limits and private reply review. Existing pantry backup/restore procedures apply to the complete shared database. A code rollback leaves the additive outreach tables present; do not run an older worker concurrently with the upgraded application or delete tables to simulate a rollback.
