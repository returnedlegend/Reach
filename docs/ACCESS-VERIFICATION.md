## Browser and backend results

`tests/access-flow.spec.ts` passed all six cases (three flows across mobile at 390 px and desktop at 1280 px). It covers geolocation denial, manual coordinate bounds and unconfigured routing; a synthetic planner response exercising constraints and map/card selection; and preview-only reviewed outreach with a synthetic reply. Planner fixture data is marked synthetic and makes no claim that a real route was measured. The reply test checks that a date-only fact of `2026-10-23` displays October 23, 2026 rather than shifting to the prior Chicago date, and that pickup hours display as 09:00–10:00 with the America/Chicago label.

The previously run retained `tests/workflow.spec.ts` and `tests/accessibility.spec.ts` suites passed 12/12 mobile/desktop cases. They cover existing listing cautions, the explicitly fictional example, trip details, text download, print, saved plans and reload, and the established accessibility screens. The planner-result axe scan found zero serious or critical violations. All access cases assert no horizontal page overflow. Screenshots from the final six-case rerun are in `docs/evidence/access-*.png`; sanitized run notes are in `docs/evidence/access-browser-qa.txt`.

After the final visual review found an oversized next-day checkbox, the planner fixture case was rerun on mobile and desktop: 2/2 passed. The checkbox rendered 24×24 px within a label at least 44 px high, with no horizontal overflow and no serious/critical axe findings. Cropped evidence is in `docs/evidence/access-{mobile,desktop}-next-day-checkbox.png`; refreshed planner screenshots include the corrected control.

`tests/access-independent.test.ts` exercises isolated SQLite behavior for verified owner-only history and private responses, explicit message authorization, cross-origin mutation rejection, recipient opt-out, rate limits, idempotent preview dispatch, expired authorization cancellation, inbound signature/sender/replay handling, quoted prior-message exclusion, changed-contact cancellation before delivery, and private availability ownership/expiry. The changed-contact case edits an opted-in test recipient after message review; dispatch cancels without invoking the sender. A quoted prior offer/date is not extracted as a new reply fact. Replies enter the planner only after the requesting owner confirms them; that review does not establish sender identity or current stock.

## Privacy and authorization assessment

The reviewed outreach path is scoped to source-backed public organization contacts entered through verified and consented enrollment. Those organization addresses are intentionally visible for review; they are not treated as private household contacts. The browser fixture uses only `example.test` recipient data. Household addresses and coordinates remain private; public directory records are not updated from household reply data. The isolated browser case checks that the confirmed availability appears only in the requesting account’s private view and leaves public pantry inventory untouched.

Authorization is explicit and time-limited. The backend tests exercise owner/session checks, authorization expiry, suppression and rate limits. The worker rechecks the reviewed recipient address before dispatch and cancels if it changed. Queue dispatch uses idempotency and does not retry uncertain leases as if delivery were known. Inbound sender identity remains unverified; signed webhook validation prevents forged/replayed requests, and quoted prior correspondence is not accepted as new facts. Prompt-injection content is treated as untrusted text, not as instructions or authorization. Private replies require owner review and confirmation before creating private availability, which expires.

No live AI inference ran. Preference assistance displayed its disabled state and allowed manual controls. No live email was sent; the worker wrote only a preview capture in the isolated temporary directory. Tests do not establish provider-side AI retention, real deliverability, recipient identity beyond the synthetic records, or live callback configuration.

## QA findings and fixes

Browser testing found nested forms in the planner: submitting manual coordinates could leave the planner and return to the home flow. The travel form now owns only its controls, and the browser suite asserts that forms are not nested. The offline itinerary is keyboard-focusable and exposed as a named region. The outreach date formatter preserves date-only calendar values and formats timestamp values in America/Chicago.

One initial outreach browser run returned HTTP 503 because the test inserted malformed pantry JSON (`{}`) without required `sources`, schedule, and connection arrays. This was a fixture defect, not a production fallback issue. The fixture now uses complete synthetic resource/planner records. Other early selector failures were corrected to target actual accessible controls; the final six-case run passed without weakening the behavior assertions.

## Limits and reproducibility

The browser server used `REACH_EMAIL_PROVIDER=preview`, `REACH_AI_PROVIDER=disabled`, and `OSM_ROUTER_MODE=disabled`, with a fresh private SQLite database and preview capture directory under `/tmp/reach-access-qa`. No live email, AI inference, route-provider request, or pantry transaction occurred. The local database’s 24 records are not proof that listed services are open, stocked, eligible, reachable, or accepting walk-ins. Source links and reported details still require confirmation by users.

Relevant checks included `npx tsc --noEmit`, `git diff --check`, the six access-flow browser cases, the 12 retained workflow/accessibility cases, and isolated access tests. The project-wide unit/type/data/build checks and parent-run live checks are reported separately by the parent agent; they are not represented here as independently rerun.
