## Behavior checks and boundaries

`tests/v3-verification.spec.ts` adds checks beyond v2's GPS, API input validation, missing-key, static-timetable and basic mobile/accessibility coverage:

- All eight cards, one selected pantry, each precise external directions link, source dates on selected details, and mobile/desktop overflow.
- No route request before explicit opt-in; changing mode, selected pantry or manual origin afterward recalculates with the current exact coordinates. The external URL changes with them.
- Quota, no-route and browser network errors show unavailable without fabricated metrics, retain external directions, and recover on retry.
- Shelter flow explicitly withholds unverified beds and invented destinations.
- Controlled Google marker events verify pantry marker → card and card → selected marker synchronization, draggable origin → current route request/URL, and script-load failure with usable fallback.

Google services are intercepted in browser tests. The map-event checks require `REACH_MAP_STUB_TEST=1` and a separate dev runtime started with **dummy** public browser configuration; their map objects are explicit test doubles. The script-error case aborts the Google script. These checks verify application behavior, not the Google SDK, billing, key authorization, provider accuracy, or an authenticated itinerary. Without that flag the two map-runtime cases are explicitly skipped; they are not counted as passed.

Authenticated Maps JavaScript, Routes and Geocoding remain **blocked by missing secure runtime configuration**. No live Google route, live BTD vehicle feed, or public school tracking integration was observed. A Google Maps directions URL is an external handoff, not an itinerary retrieved by Reach. Current key requirements and secure configuration are documented in [GOOGLE-MAPS.md](GOOGLE-MAPS.md); a value pasted in chat does not establish a securely configured runtime.
