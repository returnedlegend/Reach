# Navigation and model-provider integration research

Checked 2026-10-23 against official provider documentation, public catalogs and the implemented client. This is a research note only: no transit feed was downloaded or imported, no live inference call or authenticated account endpoint was made, and no new transit coverage is enabled. Reach currently routes scheduled transit only on BTD Route 00 Orange; see [GTFS provenance](GTFS.md), [TX-10 data audit](TX10-DATA.md), and the source/fare conflict in [ACCESS-INTEGRATIONS.md](ACCESS-INTEGRATIONS.md).

## OpenRouter: capability, cost, routing, and retry checks

OpenRouter's public [model catalog](https://openrouter.ai/api/v1/models) provides model IDs, pricing and model-level `supported_parameters`. The [model catalog API reference](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties) documents the catalog shape. For routing decisions, use the [per-model endpoints API](https://openrouter.ai/docs/api/api-reference/endpoints/list-all-endpoints-for-a-model): endpoint records expose provider-specific pricing and supported parameters. Capabilities can differ among providers for the same model and can change. A catalog/model-level `tools` or `structured_outputs` entry is therefore a candidate filter, not proof that every routed endpoint supports it.

For function tools, the request carries `tools` definitions; the model only proposes a tool call. The application must validate the proposal, decide whether to execute an allowlisted action, and return any tool result in a follow-up request. Structured output uses `response_format: {type: "json_schema", json_schema: {name, strict, schema}}`. OpenRouter documents this as supported only on selected model endpoints; use `provider.require_parameters: true` and still validate the response against Reach's local schema. Strict enforcement and accepted JSON Schema features vary by provider. See the official [tool-calling](https://openrouter.ai/docs/guides/features/tool-calling) and [structured-output](https://openrouter.ai/docs/guides/features/structured-outputs) guides.

The [provider-routing guide](https://openrouter.ai/docs/guides/routing/provider-selection) documents these relevant request controls:

- `require_parameters: true` limits routing to endpoints that support all requested parameters. Without it, unsupported parameters may be ignored.
- `data_collection: "deny"` filters providers that OpenRouter identifies as collecting data; it is not a universal zero-retention promise. `zdr: true` is the stricter endpoint filter, and may leave no matching free endpoint. Read [provider logging and data policies](https://openrouter.ai/docs/guides/privacy/provider-logging) and each selected provider's terms before disclosing user content.
- Provider routing allows fallbacks by default. `allow_fallbacks: false` disables backup providers. The separate chat `models` fallback array tries later model IDs on error; a paid model in that list can be billed even if the first model is `:free`. For a free-only request, omit the `models` fallback list and use only exact `:free` model variants. The [free-variant guide](https://openrouter.ai/docs/guides/routing/model-variants/free) says the variant is its own catalog entry with its own price and endpoint data.
- `provider.only` can restrict routing to selected provider slugs; `max_price` can set price limits for prompt, completion, request, and image pricing. Use an identified endpoint and applicable zero price limits where supported if exact provider pinning is required.

Reach's current client uses `OPENROUTER_FAST_MODEL` and `OPENROUTER_PRIMARY_MODEL` for the two roles and optional `OPENROUTER_FALLBACK_MODEL` as their explicit fallback (legacy `REACH_AI_*_MODEL` aliases are documented in [AI navigation](AI-NAVIGATION.md)). Before completion, it fetches the public catalog and requires every distinct selected/fallback model to advertise both `tools` and `structured_outputs`; in free-only mode it also requires a `:free` ID, explicit prompt/completion prices and every reported pricing value to be zero. It makes no live inference during catalog preflight. The completion body sets `data_collection: "deny"`, `allow_fallbacks: false`, and `require_parameters: true`; free-only requests also set zero `max_price` ceilings for prompt, completion, request, and image. The current features request JSON Schema structured output, not tool execution. Local schema validation remains authoritative. The catalog check is model-level evidence; `require_parameters` filters the actual endpoint, whose support and price may differ. Reach does not currently pin a provider with `provider.only`.

A public catalog lookup is only a preflight snapshot: catalog, endpoint availability, or routing can change before the request is charged, and endpoint-level prices may differ from a model summary. The catalog is not an account billing guarantee. A `:free` ID, endpoint parameter enforcement, zero `max_price` ceilings, no hidden provider fallback, and the client's explicit model choice provide stronger checks, but the account's remaining quota and enforced billing limits are account-specific. OpenRouter documents account counters at authenticated `GET /api/v1/key`; this endpoint was not called. The live account's billing state was not verified. On 2026-10-23, the public catalog returned HTTP 200 with 468 models, of which five free entries advertised both required capabilities. This is a dated observation, not a reason to hardcode model IDs or a guarantee that any entry remains available.

OpenRouter currently documents free-variant limits of 20 requests/minute and 50 requests/day for accounts with less than 10 credits purchased, or 20/minute and 1,000/day at/above that threshold; the authenticated key response reports the daily counter, while the per-minute limit is not reported there. Accounts and endpoints may be exempt. These are provider-published policies, not Reach constants or a quota guarantee. See [rate and credit limits](https://openrouter.ai/docs/api_reference/limits). Error responses use JSON `error.code`, `error.message`, and optional metadata. The docs describe 429 rate limits, 502 upstream failures, and 503 no eligible provider; `Retry-After` may be provided on 429/503 and on certain 402 in-flight-budget errors. `X-RateLimit-*` headers are sent on OpenRouter platform limit errors, not successful completions. Reach allows at most two completion attempts: a network failure or 5xx can use the configured fallback, or retry the same model if no fallback is set; a 429 or 5xx with `Retry-After` can be retried only if the delay is at most 500 ms. A longer indicated wait stops the operation. Retry attempts reserve another unit of the process-local quota, and every completion attempt counts. Other errors return to deterministic local behavior. See [errors and debugging](https://openrouter.ai/docs/api_reference/errors-and-debugging) and [AI navigation controls](AI-NAVIGATION.md).
